## 35. 0.3.2

### 35.1 Attack-clip pacing follows the sim's interval (GitHub #729)

**Seen**: an operator's attack clip was paced from a base-record guess (`bat × 100 / aspd`, no buffs), so the first swings
of a battle ran at the wrong speed until the view had measured two attacks by itself — 惊蛰's skill changing her interval
mid-battle was the reported case — and the clip then crawled toward the truth over several attacks.

**Now**: the sim pushes `['rate', unitId, seconds]` (EV.RATE) whenever a unit's own interval changes, and carries the first
value in the spawn `UnitInfo.atkInterval` (`snapshot.js`). The renderer paces the clip over that value
(`render/attackRate.js`, `SpineActor.windUp / attack`) instead of guessing. Review points from the PR review:

- **Once per change.** The "what was sent" seed is the unit's first computed interval (`units.js _recalc`), so the spawn
  value is not repeated **and the first change is not swallowed** by that seed.
- **An event outranks the spawn info.** `UnitInfo` is spawn-time metadata — ordinary snapshots do not refresh it — and the
  frame loop drains events before `sync()`. The view therefore records that an event has spoken (`rateSeen`) and stops
  adopting `info.atkInterval` after it; otherwise the stale value overwrote the event on every frame. A spawn that reuses
  the view (a 重生 / a second life) re-seeds that state (`UnitView.respawn`, `app.js` case `spawn`).
- **The clamp is a display policy.** `attackRate.js` bounds the interval at 0.2–6 s for the clip only: the sim's numbers and
  the battle result are untouched, and a unit faster than 6 attacks / s (or slower than one per 6 s) plays at the window
  edge. `[ASSUMED]`: the window has no official counterpart, the official client's own handling was not measured.
- **Stall guard.** A measured gap far from an authoritative interval is not taken as a slower rhythm (a stop, a stun, a
  redeploy, a hidden tab); only a wobble inside `ATK_JUMP_TOLERANCE` is smoothed. `[ASSUMED]` the tolerance, the drift
  share and the sanity window, all renderer-side.

Golden: the `rate` tuples are display-only state — sim results and digests do not move; the events family gained the new
tuples when the event was introduced (regenerated then, not by these review fixes).
